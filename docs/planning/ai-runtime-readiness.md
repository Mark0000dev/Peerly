API admission pool2 is separate from the future singleton worker/heartbeat pool1; core API remains independent. No SQL transaction may span inference.
- `CodexProcessExecutor`, `LinuxSandbox`, `DedicatedCredentialCache` and retained DISPLAY photo input reader exist with fake-process tests. These are adapters, not an assembled production worker. There is no AI worker entrypoint/supervised loop or deployed executor image.
- `SubscriptionCredentialCodec` is a Protocol only: no version-specific real provider credential codec exists in production source. The cache lease/refresh journal does not establish compatibility with real credentials.

The containment/tool-denial gate precedes asking the owner to authenticate from a phone. A credential-free runtime can prove synthetic-marker boundaries first; real account login is not a substitute for those proofs.

## Parent-owned phone login handoff

Only after the dedicated runtime and private credential destination are ready, parent starts device authentication in that runtime and gives the owner the current one-time link/code through the approved channel. No developer agent initiates login or reads the resulting credentials. The owner can prepare by checking that device-code login is enabled in ChatGPT security settings; no token/cache needs to be pasted or copied into repository/chat. If unavailable, parent chooses an explicitly approved supported alternative.

Official OpenAI documentation describes `codex login --device-auth`, enabling device-code login and entering the code in a browser. It also documents cached credential refresh and file/keyring storage. Those documents do not attest this application's transport/tool isolation or publish a stable credential-file schema: [Authentication](https://learn.chatgpt.com/docs/auth). Non-interactive execution can reuse cached authentication; that alone does not make a daemon safe: [Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode).
