# Approved product decisions for design v1

Status: owner-approved product baseline, 7 November 2026. Supersedes the earlier recommendations in this file and conflicting source-spec/design assumptions. These decisions describe intended implementation, not deployed functionality or a legal-compliance determination. Follow the user's latest instructions when later changes arise.

## Knowledge areas and course context — approved 9 November 2026

The MVP catalogue represents broad knowledge/help areas, not mandatory APU module enrolment. Helpers self-declare what they can help with, including knowledge acquired through another university, work or independent study. Only APU membership is verified by institutional email; no course attendance, grade or subject competence is verified by this flow.

Reuse the existing single canonical catalogue identifier as an area for deterministic relevance. A goal selects an area and describes the specific task in its existing free-text fields; a module name/code such as IDB, SSCC or BMK2 is optional task context. For example, Databases with a SQL JOIN question may match a helper who never took IDB. Preserve all existing account, pair, lifecycle, visibility and source/version permissions. The current exact identifier relevance remains explicit; the product must not claim semantic matching or equivalence that has not been implemented.

Catalogue aliases are genuine equivalent labels. A course, an entire knowledge area and an individual technology are not automatically interchangeable aliases. Future explicit course-to-area/skill mapping may improve ranking; AI may suggest classifications or task wording, but does not independently grant eligibility or certify competence. No new multi-tag taxonomy, skill graph, course verification or university integration is required for this MVP decision.

The owner approves minimal UI/copy changes required to express this direction using public Taiga mechanisms, and may request a separate redesign of this section later. Keep the domain/canonical IDs independent of the particular screen layout so that redesign does not require reimplementing matching. This approved decision supersedes the earlier plan to seed a course-name-only APU catalogue.

## Requests and deadlines

Request text is limited to 240 Unicode code points; optional note is a separate 240, goal topic/context retain 80/240. Preserve invalid overlength input for editing; no silent truncation. Server/client count consistently. Decline Undo is **10 seconds for everyone**, fixed by server deadline, unchanged by navigation/refresh. Recently declined exposes each Undo separately; no focus-based deadline extension. Pending decline occupies the unique active pair slot; no accept/new request until resolved. Eligibility is rechecked on Undo. Effective finality uses database time even if cleanup lags; cooldown starts at final decline. Submitted idempotency keys bind immutable payloads; edited resolved-failure submissions use a new intent/key.

## Capabilities

Permissions are the intersection of account lifecycle, verification/onboarding, visibility, moderation and pair state. The following rows assume no other restriction. Do not implement a single mutually exclusive enum that cannot represent combined conditions.

| State                               | Appears/browses Discover | Sends/receives new requests | Existing pending requests                                      | Existing chat read/send                                                                       |
| ----------------------------------- | ------------------------ | --------------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Normal                              | Yes/yes                  | Yes/yes                     | Normal actions                                                 | Yes/yes                                                                                       |
| Hidden voluntarily                  | No/no                    | No/no                       | Close both directions; no automatic restoration                | Yes/yes, for both participants                                                                |
| Human requires replacement photo    | No/no                    | No/no                       | Retain to ordinary expiry; no accept; decline/withdraw allowed | Yes/yes                                                                                       |
| Restricted from new contact         | No/no                    | No/no                       | Close both directions neutrally; no automatic restoration      | Yes/yes                                                                                       |
| Restricted from publishing feedback | Normal                   | Normal                      | Normal                                                         | Normal                                                                                        |
| Administrator ban                   | No/no                    | No/no                       | Close both directions                                          | Owner retains support/legal route; peer history readable, no new messages in either direction |
| Deleted by user                     | No/no                    | No/no                       | Close both directions                                          | No owner session; peers keep history with Deleted account, no new messages                    |

Hiding is discovery/new-contact visibility only; it never freezes accepted conversations or hides the counterpart's normal existing chat context. Restoration rechecks all other restrictions and never reopens closed requests. Photo replacement imposed by a human requires human approval of the new photo before exposure resumes; AI photo advice is nonbinding. An admin ban is an explicit audited administrator action with reason/review route, distinct from deletion; do not add further speculative suspension modes. Ban stops all student product actions including AI/feedback; limited support/legal/account-management access may remain through a restricted authenticated state. Lifting ban never removes deletion or other restrictions.

## User account deletion: soft delete only

Add Delete account in account settings with a normal confirmation and success/sign-out state. User-facing copy: Delete account / Your account has been deleted. Do not claim all stored data is erased. Detailed retention explanation belongs in Terms/Privacy, not extra registration/deletion banners or legal checkboxes.

A committed deletion marks `deleted_at`, records the deletion action, revokes all sessions/login transactions and unused verification challenges, removes exposure/contact, closes pending requests, cancels owned pending AI/delivery intents where no longer appropriate, and prevents further account activity. Disable login reactivation/recreation by retaining issuer/sub and institutional-email uniqueness. A subsequent Google login yields a safe account-unavailable/support outcome, not a fresh active account. No self-service restore or automatic email reassignment is in scope; privileged inspection is available but does not itself authorise reactivation.

Ordinary users see Deleted account with a neutral avatar instead of the deleted person's identity/profile; previously exchanged messages remain visible to their participants, with actions appropriately disabled. Private message content may itself include identity and is not rewritten. Product lists/search/catalogue/recommendations, pending notifications, existing SSE sessions and cache invalidation must enforce deletion. Operators see the complete original profile, messages/files, relationships, events, audit and analytics, with deleted status/time clearly marked. Do not anonymise the internal account/analytics linkage or cascade-delete business records.

All accumulated business records, media, canonical events, analytics and audit remain stored after deletion. Soft delete is not an erasure request. Do not implement automatic purge/anonymisation of this retained history. Any future actual erasure process needs a separate explicit policy; do not silently relabel soft deletion as physical erasure. Authentication secrets, expired OTP delivery envelopes, temp files and disposable transport caches still have their security cleanup: they are not retained product history.

## Registration, Terms and Privacy

No dedicated legal onboarding step, consent checkboxes, notice-acknowledgment control or analytics preferences/opt-out. At the explicit registration action show only concise inline copy with accessible links, such as: “By creating an account, you agree to our Terms of Use and Privacy Policy.” Full conditions, identified mandatory analytics/traces, privileged access, AI processing, retention including soft deletion and rule updates live in those pages.

Bind actual document versions and displayed wording to the one-use registration/login transaction; record a registration-under-terms event/receipt when the user completes the applicable registration action. No record claiming a checkbox was ticked, explicit optional opt-in or that the user read a document. Google-provider consent is not an application policy receipt. Never manufacture receipts for historical users. Technical Google identity creation is not itself proof that the registration notice was displayed; the server requires a genuine registration context before activation. Reauthenticate returning users without repeatedly registering them or showing a consent gate.

Analytics is a mandatory part of the product, account-linked with full meaningful action/request/job/trace correlation. No optional analytics mode or choice field drives collection. Gather explicit interactions/navigation/outcomes and technical errors/performance; no keystroke, DOM/session recording or arbitrary body capture was added by this decision. Private text/images remain in business storage, not telemetry. Anonymous landing visits cannot be falsely assigned an identity; link authenticated activity accurately. Deleted users produce no further active sessions/events, while all prior analytics remains linked and inspectable.

Terms/Privacy updates produce a concise informational notification linking the changed document/summary, no reacceptance, blocking screen, seven-day grace or analytics reconfirmation. Record document publication, notice delivery/read/dismissal where actually observed, separately from original registration; never rewrite original receipts to claim acceptance of a later version. No separate marketing-style prompt. This is the approved UX; final authored documents still need actual operator/provider/contact facts.

## Operators and history

Owner and explicitly designated developers have exhaustive privileged access without a case restriction; audit sensitive reads. Grafana is visible to the owner/developer team; it does not itself grant application operator privilege. Search spans Google-linked account and university email identifiers, user/resource IDs, names where applicable, conversations/participants, requests/messages/files/reports and operation/request/trace/action IDs. Filter by active/deleted/banned state and time. Full data and reverse relationships are paginated; no giant eager graph query. Free-text message-content search or bulk export is not implied; message ID/conversation/participant lookup and viewing full authorised history suffice.

Use cursor pagination, previous/next/load more, server-supported counts only. Link user -> activity -> operation -> trace/log -> business record bidirectionally; retain original identity internally for deleted accounts. Full trace collection targets 100% of instrumented meaningful requests/actions with bounded resources, durable export buffering and explicit loss/gap alerts; do not promise physically impossible zero loss. Preserve collected trace/log/analytics history via archive before hot-store expiry, not silent TTL destruction. Operational storage sizing, encrypted archive placement, retrieval/indexing and restore must be measured and tested before pilot.

## 10 November 2026 — fresh registration after self-deletion

Owner explicitly supersedes the earlier prohibition on automatic re-registration after deletion. A fresh authenticated Google sign-in may create a NEW account after the prior account was soft-deleted. Keep the old account, identity/mail association history, all business records, relations and accumulated analytics internally. No prior sessions, membership proof, registration acceptance, chats, content, role or profile authority transfers to the new account. The new account completes current registration and fresh institutional-mail verification. Preserve concurrency-safe single active claims and enforce existing bans; deletion/re-registration is not a ban bypass. Retired identity/mail associations must remain linked to their original account rather than being overwritten, deleted or rewritten with artificial addresses.

University Outlook quarantine is a confirmed user-reported onboarding issue. An SMTP accepted/delivered transport state is not proof of inbox placement. Verification/help UI must explain possible quarantine, link the official Microsoft portal with tenant-policy caveats and support, preserve server cooldown/expiry and never bypass mailbox proof. Sender authentication/reputation/quarantine diagnosis is separate from copy changes; headers are needed before claiming the root cause is fixed.

### 10 November — technical alert destination

Owner explicitly selected the existing Peerly Dev Telegram group for technical alerts (availability, errors and queue failures). Use grouped/deduplicated firing and resolution notifications; no student message bodies, prompts, email addresses or credentials in alerts. This authorises the technical alert path in addition to the earlier staging announcement. Do not restart the legacy shared Alertmanager blindly: it is currently stopped and may have unrelated historical routes. Add the scoped Peerly integration while preserving other projects.
