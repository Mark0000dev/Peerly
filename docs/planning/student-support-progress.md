## Implemented contracts

- `GET /api/v1/me/notification-preference`, `PUT` with `{mode,expected_version}`, session Origin/CSRF/idempotency. Modes exactly `messages_and_requests` / `all_updates`; absent row is truthful default version 0, timestamp null. Changes append immutable versions; no-op keys retain original default/revision. Conflicting reuse and stale CAS reject. Actual account lock serializes writers. No OS permission, push registration/delivery, mandatory security email or mandatory analytics switch.
- Native push transport belongs to the separate native rollout. Saved preference is not proof of delivery capability. Optional updates must consult the actual current preference when a transport is implemented; this slice sends nothing.
- `POST /api/v1/support-context` with closed `{}` and exact public Origin creates/reuses a seven-day opaque Secure/HttpOnly/SameSite=Strict proof cookie and returns only its CSRF token/expiry. The existing browser signer handles CSRF syntax; the support credential never authenticates identity or deletion recovery. Network peer is parsed as an IP; arbitrary forwarded headers are not trusted. New contexts: ten per source per rolling hour.
- Public `POST /api/v1/support-cases` requires the proof, exact public Origin, support CSRF and idempotency key; body topic, reply_address, message, optional details. Topics include sign-in, verification delivery/address, already-used email, deleted account and other. Maximum lengths 254/4000/2000; private text is business storage only. Five cases per source per rolling day and five per proof, serialized by source advisory lock and proof row lock. Replay precedes quota and returns original revision, even after operator changes.
- `GET /api/v1/support-cases/{case_id}` requires the same live proof and returns only actual status/version/timestamps; unknown, foreign and expired proof all return the same unavailable response. UUID or reply address grants nothing. Reload can recover CSRF through support-context while the cookie lives. Losing/expiring this proof requires a new request; no invented email link or email recovery channel.
- `GET /api/v1/support-cases` recovers recent receipts from the live proof without a remembered case ID or idempotency key. `GET /api/v1/me/support-cases` recovers the real actor’s recent receipts, including restricted unverified/banned accounts. Both return only receipt metadata, at most 20 ordered by received_at/id descending; neither claims a full-history listing. A proof can create at most five cases. Actor projection has its own actor/received/id index.
- `POST /api/v1/me/support-cases` additionally uses the existing real session Origin/CSRF guard to bind an actual authenticated actor; unverified/banned accounts may request help. `GET /api/v1/me/support-cases/{case_id}` checks original actor ownership. Deleted/no-session users use the public proof path. Reply address never activates, merges or rebinds an account.
- Minimal operator detail `GET /api/v1/operator/cases/{case_id}` and CAS/idempotent `PUT /api/v1/operator/cases/{case_id}/status`. Existing explicit operator grant and session guard, metadata-only inspection audit in the same transaction, real operator/grant reference on later revisions. No global-inspection case gate. No operator UI, list/search platform, public resolution narrative, alerts, outbound mail or Telegram.
